# Browser demo — maintainer notes

How the "Try Drift in your browser" demos are built and launched.

## The model

Each demo lives at `demos/<ecosystem>/` and is committed at the **old**
dependency version, with source code valid against it. `demos/<ecosystem>/demo.json`
declares the upgrade as a literal find/replace on the manifest — deliberately not
a patch file, since a demo upgrade is one version string and a plain replacement
can't go stale the way a diff can. A per-ecosystem devcontainer applies that edit
**once, at creation time**, via `node scripts/prepare-demo.mjs <ecosystem>`. The
application source is never touched.

Drift then analyses an ordinary uncommitted manifest change — the exact
situation a developer is in mid-upgrade. Nothing in Drift knows this is a demo.

## Devcontainer lifecycle

`onCreateCommand` runs the prepare step — `node scripts/prepare-demo.mjs
<ecosystem>` for most demos, or a longer `setup` command from
`scripts/lib/devcontainer-spec.mjs` for the few that need something installed
first (a package manager, or — for Cargo — the nightly toolchain and
`cargo-public-api` that Drift's Rust surface diff needs, provisioned up front so
the panel isn't blank for minutes on first analysis; see
`.devcontainer/cargo/setup.sh`):

```
node scripts/prepare-demo.mjs <ecosystem>
```

Each `onCreateCommand` ends by installing the CLI globally
(`npm install -g @usedrift/cli`), because the demo is both halves of Drift and a
visitor who has to install something first has not had the demo. Every container
has Node already — the shared prepare script is Node — so this costs one npm
install and no extra image.

`onCreateCommand` is used deliberately:

- it runs **after** the repository is checked out;
- it runs **once, during creation**, before the editor and the Drift extension
  start (`waitFor` is set to it), so the dependency files are already dirty
  when startup analysis runs;
- it does **not** run on resume, so reopening a Codespace never re-applies the
  patch over the visitor's own experiments.

Resume-time behaviour is intentionally left as the devcontainer default: nothing
runs.

## Starting both halves without a click

Two things have to be running before the visitor does anything, or the demo is a
repository with a README about a tool they cannot see:

- **the panel** — `drift.ui.openOnStartup: true` reveals the Drift view as the
  window opens. The extension reveals it *before* the startup analysis rather
  than after, so the visitor watches the analysis happen instead of arriving at
  a finished verdict with no idea what produced it. The setting is off by
  default in the extension; prepared environments are what it exists for.
- **the CLI** — `postAttachCommand` runs `drift analyze --dir demos/<ecosystem>`
  and its output lands in a real terminal in the editor. `postAttach` rather
  than `postCreate` because it runs on resume too, and scoped with `--dir` so it
  analyses the one demo rather than all sixteen.

## Workspace focus

The Git root stays at the repository root, because that is what Drift's
manifest-range detection expects. Each devcontainer instead sets
`files.exclude` for the other four demo directories, so the Explorer shows only
the relevant demo without changing anything Drift relies on.
`customizations.codespaces.openFiles` opens `DEMO.md`, the affected source file,
and the manifest.

## Extension settings

- `drift.session.mode: "ask"` — Drift analyses and explains; it never edits.
  No agent, API key, or GitHub auth is involved.
- `drift.analysis.runOnStartup: true` — the default, set explicitly.
- `drift.ui.openOnStartup: true` — open the panel without a click. See above.
- `drift.analysis.includePatch: true` — **go only**. `golang.org/x/exp` ships
  only pseudo-versions, which Drift classifies as patch moves.

## Deep links

Every demo's launch link is GitHub's standard Codespaces deep link for its
devcontainer:

```
https://codespaces.new/trydrift/demo?quickstart=1&devcontainer_path=.devcontainer%2F<ecosystem>%2Fdevcontainer.json
```

The README's demo table carries the full set, generated by
`node scripts/make-readme.mjs` so it can't drift from the devcontainers that
actually exist.

The links depend on two published artifacts: `drift.drift` on the VS Code
Marketplace and `@usedrift/cli` on npm. Until a release has published both, a
Codespace will come up with no extension and no `drift` on the PATH — the
fixture will be correct and nothing will analyse it. Neither has been exercised
through the real Codespaces create flow yet; the first launch after publishing
is a genuine smoke test, and the things most likely to be wrong are the global
npm install on the images that get Node from a feature rather than the base
image (opam, pub, swift, hex) and whether `postAttachCommand` output lands where
these notes claim it does.

## Cost

Codespaces are created under the visitor's own GitHub account and count against
the visitor's own Codespaces allowance. The `trydrift` organisation configures
no billing, no spending limit, no payment method, and no prebuilds. Startup
cost is kept down by small fixtures, per-ecosystem images, and installing only
what each demo needs.
